# 第2章：应用层 —— 现代网络价值的核心

作为自顶向下（Top-Down Approach）教学模型的起点，应用层不仅是用户直接互动的界面，更是计算机网络创新最活跃、产出最高的领域。在软件定义网络（SDN）将控制平面（Control Plane）与数据平面（Data Plane）分离的现代架构中，底层设施的演进很大程度上是由应用层日益增长的复杂需求驱动的。

## 2.1 网络应用原理

> **背诵提纲** → [2.1 小节 study.md](./2.1_network_application_principle/study.md)（C/S vs P2P + 四大需求选 TCP/UDP + [易错表](./2.1_network_application_principle/study.md#ch2-1-exam)）

### 2.1.1 战略背景：创新的策源地

应用层是因特网对终端用户直接交付价值的场所。选择从这里开始探索，是因为应用层在很大程度上定义了网络基础设施的演进路径。从早期的文本邮件到如今的超高清实时流媒体，应用层协议的演进直接推动着底层运输层与网络层的资源分配与优化方向。

### 2.1.2 核心架构对比：C/S 与 P2P

在现代网络工程中，选择何种应用体系结构直接决定了系统的**可扩展性（Scalability）**上限、**可靠性**与**运营成本**。两大经典模型为：**客户-服务器（C/S，中心化）**与**对等网络（P2P，去中心化）**。

#### 一、核心定义

- **C/S（Client–Server）**：严格主从架构。**服务器常在线、地址固定、集中提供服务**；客户端仅发起请求、消费服务，**客户之间不直接通信**。
- **P2P（Peer-to-Peer）**：对等分布式架构。**所有节点地位平等**，既是客户端也是服务器，**可直接互相通信、共享资源**，无强制中心节点。

#### 二、详细对比表（考试重点）

| 特性 | 客户-服务器架构（C/S） | 对等架构（P2P） |
|------|------------------------|-----------------|
| **角色划分** | 明确：客户（请求者）+ 服务器（提供者） | 无区分：节点互为客户/服务器 |
| **在线要求** | 服务器**必须常在线**；客户端按需上线 | 无强制中心，节点可随时上下线 |
| **可扩展性** | 垂直扩展贵；服务器易成**单点瓶颈** | **自扩展**：用户越多，整体能力越强 |
| **可靠性** | 存在**单点故障**：服务器宕机则服务不可用 | 无单点故障；多节点冗余，抗毁性强 |
| **数据存储** | **集中存储**在服务器，一致性高 | **分散存储**在各节点，一致性难保证 |
| **安全与管理** | 集中管控，**安全策略易统一、易审计** | 分布式治理，安全复杂、监管难 |
| **成本结构** | 数据中心、带宽、运维成本高 | 基础设施成本低（治理/合规成本高） |
| **典型场景** | Web、邮件、数据库、网银、企业系统 | BT/迅雷、直播/视频分发、区块链、IM |

#### 三、优缺点速记（面试/简答）

**C/S 优点**

- 集中管理、数据一致、安全可控、易维护。
- 服务质量（QoS）易保障、易计费、易追溯。

**C/S 缺点**

- 服务器**单点瓶颈 + 单点故障**。
- 扩展成本高、带宽压力集中。

**P2P 优点**

- **高可扩展、无单点、资源利用率高**。
- 大规模分发成本极低（利用用户上行带宽）。

**P2P 缺点**

- 管理难、安全风险高、数据一致性弱。
- 节点不稳定、内容不可控、合规风险大。

#### 四、一句话总结（背诵句）

- **C/S**：中心化、强一致、易管控，但**瓶颈 + 单点故障、成本高**。
- **P2P**：去中心化、自扩展、低成本，但**管理难、安全弱、一致性差**。

### 2.1.3 进程通信与套接字（Socket）

**网络通信的实质**  
网络通信的实质是运行在不同端系统上的**进程（Process）**之间的信息交换。主机只是承载进程的载体，真正收发数据的是两端的应用进程。

**套接字接口（Socket Interface）**  
- 套接字是**应用进程与运输层之间的 API**，是网络编程的核心接口。  
- 架构上可抽象为**通信门户/端点**：进程通过这个「门户」向网络发送报文或从网络接收报文。  
- 在 Unix/Linux 中，Socket 被抽象为一种特殊文件描述符，可用 `read` / `write` / `close` 等文件 I/O 方式操作。

**端点标识：IP + 端口**  
要在网络中唯一标识一个进程，需要：  
- **IP 地址**：定位到网络中的某台**主机**；  
- **端口号（Port）**：定位到该主机上的某个**进程/套接字**。

因此：  
- **Socket 地址 = IP 地址 + 端口号**；  
- 一个完整 TCP/UDP 连接由**四元组**唯一确定：`{源IP, 源端口, 目的IP, 目的端口}`。

**Socket 的作用与地位**  
- 既支持**跨网络不同主机**的进程通信，也支持**同一主机内进程通信**（UNIX 域套接字）；  
- 屏蔽了底层 TCP/IP 协议栈的复杂细节，为应用程序提供统一、简洁的网络编程接口。

**传输层协议与 Socket 类型（简要）**  
- **TCP（SOCK_STREAM）**：面向连接、可靠、字节流，如浏览器、文件传输；  
- **UDP（SOCK_DGRAM）**：无连接、不可靠、数据报，如视频通话、直播、游戏。

### 2.1.4 运输层服务需求分析

作为架构师，需按应用特性评估对运输层的典型需求维度：

1. **可靠数据传输**：如文件传输要求完整性；VoIP 等可容忍少量丢包。
2. **吞吐量（Throughput）**：实时视频对可用带宽有下限，属**带宽敏感**；邮件等多为**弹性**应用。
3. **定时（Timing）**：交互式游戏、低时延交易对时延极敏感。
4. **安全性**：机密性、完整性、身份鉴别等（常由 TLS 等在应用或会话层协同实现）。

**新手避坑**：区分「**应用层协议**」与「**Web 缓存**」。协议（如 HTTP）定义报文语法与语义；缓存（代理/CDN/浏览器缓存）是**部署与中间件策略**，遵循协议，但目的在减少冗余传输与靠近用户。

## 2.2 Web 和 HTTP

> **背诵提纲** → [2.2 小节 study.md](./2.2_http_and_web/study.md)（[文本协议 vs IP](./2.2_http_and_web/study.md#ch2-http-message-diagram) · [四段结构](./2.2_http_and_web/study.md#ch2-http-message) · [HTTPS 载荷](./2.2_http_and_web/study.md#ch2-http-tls-payload) · [口诀](./2.2_http_and_web/study.md#ch2-2-exam)）

### 2.2.1 战略背景：从文档传输到商业基石

超文本传输协议（**HTTP**）已从早期简单文档交换，演变为支撑商业、社交与云服务的核心载体之一。

### 2.2.2 连接演进：RTT 消耗分析

#### 核心概念：RTT

**RTT（Round-Trip Time，往返时间）**：一个小数据包从客户端到服务器、再返回客户端的时间，包含传播延迟、排队延迟、处理延迟等。

#### TCP 三次握手与 RTT（易错考点）

> 常见表述「三次握手 = 1 RTT」：**做题可简化**；**严格应为 1.5 RTT**。

**标准过程 + RTT 拆解（必背）**

1. **Client → Server：SYN**（seq=x）
2. **Server → Client：SYN+ACK**（seq=y, ack=x+1）→ 前两步合计 **1 RTT**（一去一回）
3. **Client → Server：ACK**（ack=y+1）→ 第三步 **+0.5 RTT**  
   **严格合计：1.5 RTT**。

**第三次 ACK 可携带 HTTP 请求（必背）**

- **SYN、SYN+ACK 不能带数据**（防攻击、连接未就绪）。
- **第三次 ACK 可以带数据**（客户端已进入 ESTABLISHED；RFC 793 允许）。
- 因此可把 **ACK 与 HTTP GET 同发**，握手估算常**简化为 1 RTT**（0.5 RTT 握手与数据发送合并）。

**HTTP 非持续连接经典结论**

- 握手：**1 RTT（估算）** + HTTP 请求–响应：**1 RTT** → **总计 2 RTT**（下文各模式均在此基础上展开）。

**一句话背诵**

- **严格：TCP 三次握手 1.5 RTT；做题：简化为 1 RTT。**
- **第三次握手（ACK）可携带 HTTP 请求，故 HTTP 非持续连接单对象常记 2 RTT。**

---

#### 1）非持续连接（Non-persistent，HTTP/1.0 默认）

**工作机制**

- **每个对象单独建连、传完即关**：1 个 TCP 连接只传 1 个请求–响应对。
- 流程：**三次握手（≈1 RTT，严格 1.5）→ HTTP 请求–响应（1 RTT）→ 关闭连接**。

**RTT 消耗（串行，无并行）**

- 单个对象：**2 RTT + 传输时间**
- 页面含 **N 个对象**：**总 RTT ≈ 2N RTT**（每个对象都要握手 + 请求响应）

**特点**

- ✅ 简单、隔离性好
- ❌ **握手开销巨大**：小对象场景下 RTT 占比极高；N 越大越慢
- ❌ 服务器负担重（频繁建连/断连）

---

#### 2）持续连接（Persistent，HTTP/1.1 默认 Keep-Alive）

**工作机制**

- **一次建连、复用多次**：TCP 连接默认不关闭，可传多个请求–响应对。
- 分两种模式：**非流水线（默认）、流水线（Pipelining）**。

**2.1 持续连接：非流水线（without pipelining）**

- 规则：**必须等前一个响应返回，才能发下一个请求**。
- RTT 消耗（N 对象）：
  - 首次握手：**1 RTT**
  - 每个对象请求–响应：**1 RTT**
  - **总 RTT ≈ 1 + N RTT**
- 相比非持续：**节省 (N−1) 次握手 RTT**，但仍需逐个等响应。

**2.2 持续连接：流水线（Pipelining）**

- 规则：**连续发多个请求，无需等待前一响应**；服务器按序返回响应。
- RTT 消耗（N 对象）：
  - 握手：**1 RTT**
  - 批量请求–响应：**1 RTT**
  - **总 RTT ≈ 2 RTT**（与 N 无关）
- 理论最优，但**实践几乎不用**。

**流水线失效原因（考试重点：队头阻塞 HOL Blocking）**

- **HTTP 层队头阻塞（HOL）**：响应必须按请求顺序返回；**第一个响应慢，后面全卡住**。
- 中间代理/防火墙兼容性差、出错难恢复。
- 现代浏览器**默认关闭流水线**，改用**多并行 TCP 连接**（通常 6–8 个）提升速度。

---

#### 3）三种连接 RTT 对比（背诵表）

假设页面含 **N 个对象**，传输时间忽略：

| 连接类型 | 核心特点 | 总 RTT（近似） | 适用场景 |
|----------|----------|----------------|----------|
| 非持续（HTTP/1.0） | 每对象一连接，串行 | **2N RTT** | 早期、小资源 |
| 持续非流水线（HTTP/1.1 默认） | 同连接复用，逐请求等待 | **1 + N RTT** | 主流、兼容性好 |
| 持续流水线（理论） | 同连接批量发请求 | **2 RTT** | 几乎不用（HOL） |

---

#### 4）一句话总结（简答题直接写）

- **非持续**：每次都握手，**RTT 随对象数线性暴涨**。
- **持续非流水线**：一次握手、逐个请求，**RTT 显著降低**。
- **流水线**：理论最优（仅 2 RTT），但因**队头阻塞**，现代浏览器基本废弃。

### 2.2.4 状态管理（Cookies）

#### 1）背景

- **HTTP 是无状态（stateless）**：每次请求独立，服务器默认「不认识」客户端，无法记住登录、购物车、偏好等状态。
- **Cookie 作用**：在**客户端保存少量状态**，让服务器识别同一用户，实现「有状态会话」。

#### 2）核心工作流程（必背）

1. **首次请求**：浏览器 → 服务器，**无 Cookie**。
2. **服务器下发 Cookie**：响应头带 **Set-Cookie**，格式示例：

   ```http
   Set-Cookie: session_id=abc123; Path=/; HttpOnly
   ```

   浏览器**本地存储** Cookie。
3. **后续请求**：浏览器自动在请求头带上 **Cookie**：

   ```http
   Cookie: session_id=abc123
   ```

4. **服务器识别**：读取 Cookie，判断是同一用户，维持登录/会话。

#### 3）典型用途（简答）

- ✅ **会话管理**：登录态、Session 绑定。
- ✅ **个性化**：主题、语言、偏好设置。
- ✅ **用户跟踪**：浏览行为、广告归因。

#### 4）一句话总结

**Cookie = 服务器发给浏览器的「身份小纸条」，每次请求自动带上，解决 HTTP 无状态问题。**

### 2.2.5 Web 缓存与条件 GET

#### 1）缓存目的

- 减少**延迟、带宽消耗、服务器负载**。
- 代理/浏览器缓存静态资源（图片、CSS、JS）。

#### 2）两类缓存（考试重点）

**① 强缓存（直接用，不询问服务器）**

- 响应头：**Cache-Control（HTTP/1.1）、Expires（HTTP/1.0）**。
- `Cache-Control: max-age=3600`：1 小时内直接用缓存，**不发请求**。

**② 协商缓存（条件 GET，必背）**

强缓存过期后，**发请求问服务器：资源变了吗？**  
核心：**304 Not Modified**（没变化，返回空，用本地缓存）。

两种实现（对比题常考）：

1. **Last-Modified + If-Modified-Since（基于时间）**
   - 响应：`Last-Modified: 2026-05-16 10:00:00`。
   - 请求：`If-Modified-Since: 2026-05-16 10:00:00`。
   - 缺点：**秒级精度、内容不变但时间变会误判**。

2. **ETag + If-None-Match（基于内容指纹，推荐）**
   - 响应：`ETag: "abc123"`（内容哈希）。
   - 请求：`If-None-Match: "abc123"`。
   - 优点：**精确到内容，无时间戳问题**。

#### 3）一句话总结

**条件 GET = 缓存过期后「问服务器」，没更新返回 304，省流量省时间。**

### 2.2.6 协议升级：HTTP/2 与 HTTP/3

#### 1）HTTP/1.1 痛点（铺垫）

- 队头阻塞（HOL）：一个请求慢，后面全堵。
- 连接数限制（浏览器默认 6–8 个）。
- 头部重复、冗余大。

---

#### 2）HTTP/2（TCP 上的大升级）

**核心特性（必背）**

1. **二进制分帧**：文本 → 二进制帧，**更小、更高效、易解析**。
2. **多路复用（Stream ID）**：**一个 TCP 连接跑多个请求/响应**，互不干扰；突破 6 连接限制。
3. **头部压缩（HPACK）**：重复头部压缩，**减少 50–80% 头部体积**。
4. **优先级与服务器推送**：可指定资源优先级；服务器可主动推资源（Push）。

**局限**

- 仍基于 **TCP**：**TCP 层队头阻塞仍存在**——一个流丢包，整个连接卡住。

---

#### 3）HTTP/3（QUIC + UDP，革命性）

**核心：抛弃 TCP，改用 QUIC（UDP 之上）**

**关键改进（对比题必背）**

1. **彻底消除队头阻塞**
   - QUIC 用**独立流（Stream）**，每个流独立传输、独立丢包重传。
   - **A 流丢包 ≠ B 流卡住**，弱网/丢包环境性能大幅提升。

2. **极速握手（0-RTT / 1-RTT）**
   - HTTP/2：TCP + TLS 常约 **2 RTT**（TLS 1.3 可更短）。
   - HTTP/3：首次常 **1 RTT**，会话恢复可达 **0-RTT**（有重放风险，需业务侧权衡）。

3. **连接迁移**
   - 用 **Connection ID** 标识连接，**IP/端口变了（Wi-Fi→5G）连接可不断**。

4. **内置 TLS 1.3**
   - 加密与传输一体化，**默认安全、更快更简单**。

---

#### 4）HTTP/1.1 vs HTTP/2 vs HTTP/3（背诵表）

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3（QUIC/UDP） |
|------|----------|--------|---------------------|
| 传输层 | TCP | TCP | **QUIC（UDP）** |
| 多路复用 | 无（6 连接限制） | 单连接多流 | 单连接多流，**无 HOL** |
| 队头阻塞 | 严重 | 仍有（TCP 层） | **彻底解决** |
| 握手延迟 | 3–4 RTT | 约 2 RTT | **0–1 RTT** |
| 头部压缩 | 无 | HPACK | QPACK（更优） |
| 连接迁移 | 不支持 | 不支持 | **支持** |

#### 5）一句话总结

- **HTTP/2**：TCP 上做二进制 + 多路复用，缓解 HOL，但没根治。
- **HTTP/3**：换 QUIC + UDP，**彻底解决队头阻塞 + 0-RTT 握手 + 连接迁移**，弱网表现更强。

### 2.2.7 工程实践建议

减少请求数（合并资源、内联等）与合理配置 **Cache-Control** 仍是前端/网关侧常见优化手段（需权衡可缓存性与新鲜度）。

## 2.3 因特网中的电子邮件

> **背诵提纲** → [2.3 小节 study.md](./2.3_email_smtp_pop3_imap/study.md)（架构 + SMTP/POP3/IMAP/MIME + [考试速记](./2.3_email_smtp_pop3_imap/study.md#ch2-3-exam)）

### 2.3.1 战略背景：异步系统与整体链路

- **电子邮件 = 典型异步通信系统**：发信与读信时间完全**解耦**。
- **用户侧**：一般用 **POP3/IMAP 拉取（Pull）** 或 **Web（HTTP）** 访问。
- **服务器侧**：**SMTP 负责推送转发（Push）**。
- **完整链路（必背）**：  
  **用户代理 MUA → 发送邮件服务器 →（SMTP 中继）→ 接收邮件服务器 → 用户代理 MUA**

---

### 2.3.2 SMTP 协议深度剖析（核心考点）

**SMTP（Simple Mail Transfer Protocol，简单邮件传输协议）**

- **作用**：**发送 + 服务器间转发邮件**（只负责「送」，不负责「存/读」）。
- **传输层与端口（必背）**：
  - TCP 端口 **25（明文）**
  - 加密：**465（SSL）、587（TLS/STARTTLS）**
- **交互模式**：**命令-响应（文本行）**，服务器返回**三位状态码**（220/250/354/221…）。
- **核心命令（必背顺序）**：
  1. **HELO/EHLO**：客户端打招呼、报身份
  2. **MAIL FROM**：发件人（信封地址，用于退信）
  3. **RCPT TO**：收件人（可多个）
  4. **DATA**：开始传输邮件内容（头部 + 正文）
  5. **.（单独一行）**：结束内容
  6. **QUIT**：关闭连接
- **持续连接**：同一 TCP 连接可发**多封邮件**，不用每次重连，节省 RTT。
- **SMTP 本质**：**推（Push）协议**——主动把邮件一站一站推到目标服务器。

---

### 2.3.3 报文格式与 MIME（必考）

#### 1）原始 SMTP 局限

- 只支持 **7-bit ASCII**：不能传中文、图片、附件、HTML。

#### 2）MIME（Multipurpose Internet Mail Extensions）

- **定位**：**不是独立协议，是 SMTP 的扩展标准**，不改 SMTP 本身。
- **核心作用**：把**二进制/非 ASCII 数据编码成文本**，让 SMTP 能传输。
- **五大 MIME 首部（必背）**：
  1. **MIME-Version: 1.0**（必须有）
  2. **Content-Type**：内容类型（text/plain、text/html、image/jpeg、multipart/mixed 多部分）
  3. **Content-Transfer-Encoding**：编码方式（**base64** 最常用，二进制→文本）
  4. **Content-Id**：唯一标识
  5. **Content-Description**：内容说明（如「附件：照片.jpg」）
- **一句话总结**：**MIME = 让 SMTP 能发中文、HTML、图片、附件的「翻译官」**。

---

### 2.3.4 邮件访问协议对比（高频选择/简答）

**SMTP 只管发；收信/读信靠下面三类协议**。

#### 1）POP3（Post Office Protocol v3）

- **端口**：110（明文）、995（SSL）
- **核心特点**：**下载并删除（默认）**
  - 邮件从服务器**下载到本地**，服务器通常**删除副本**
  - 适合**单设备、离线阅读**
- **缺点**：**多设备状态不同步**（已读/未读、文件夹、标记都不统一）

#### 2）IMAP（Internet Message Access Protocol v4）

- **端口**：143（明文）、993（SSL）
- **核心特点**：**服务器常驻、状态同步**
  - 邮件**默认留在服务器**，客户端只看副本
  - **跨设备完全同步**：已读/未读、删除、移动、文件夹一致
- **优点**：**多设备、云邮箱标准**（Gmail/QQ 邮箱都支持）

#### 3）HTTP（Web 邮件）

- **本质**：浏览器通过 HTTP/HTTPS 访问**Web 邮箱页面**
- **特点**：
  - 无需配置客户端，**任何设备浏览器即用**
  - 后端仍依赖 SMTP/POP3/IMAP，HTTP 只是「前端入口」

#### 对比表（背诵）

| 协议 | 核心机制 | 服务器留存 | 多设备同步 | 典型场景 |
|------|----------|------------|------------|----------|
| **SMTP** | 推送（发信/转发） | ❌ 不存 | — | 邮件发送、服务器间中继 |
| **POP3** | 下载 + 删除 | ❌ 默认删除 | ❌ 弱 | 单设备、离线、老客户端 |
| **IMAP** | 在线管理、同步 | ✅ 永久留存 | ✅ 强 | 多设备、云邮箱、现代办公 |
| **HTTP** | Web 页面访问 | ✅ 服务器存 | ✅ 靠后端 | 浏览器邮箱、公共机房 |

---

### 2.3.5 一句话总览（简答题直接写）

- **SMTP**：负责把邮件**推出去、传到底**；
- **MIME**：让 SMTP **能传中文、附件、多媒体**；
- **POP3**：**下载到本地、单设备用**；
- **IMAP**：**服务器托管、多设备同步**；
- **HTTP**：**浏览器直接看邮件**。

## 2.4 DNS：因特网的目录服务

> **背诵提纲** → [2.4](./2.4_dns_service/study.md)（四层 · 递归/迭代 · RR · [12 步流程](./2.4_dns_service/study.md#ch2-4-flow) · [易错](./2.4_dns_service/study.md#ch2-4-exam)）

### 2.4.1 战略背景

DNS 将**主机名映射为 IP 地址**（及其他记录）。单一中心不可扩展，因此是**分布式、层次化**数据库。

### 2.4.2 层次结构

1. **根 DNS 服务器**：指向 TLD 服务器  
2. **顶级域（TLD）服务器**：如 `.com`、`.org`、`.cn`  
3. **权威 DNS 服务器**：由组织/服务商维护，存放该域名的权威记录  

（教材中还常介绍**本地 DNS / 递归解析器**角色。）

### 2.4.3 查询机制：递归与迭代

典型模型：**主机 stub resolver → 本地 DNS（递归解析器）** 常采用递归查询；解析器向上游（根/TLD/权威）的迭代/转发组合依实现而定。总体目标：**把查询负载从根分散开**。

### 2.4.4 资源记录（RR）

存储格式可记为 `(Name, Value, Type, TTL)`。

| Type | Name 含义 | Value 含义 |
|------|-----------|-------------|
| A | 主机名 | IPv4 地址 |
| NS | 域名 | 该域的权威 DNS 主机名 |
| CNAME | 别名 | 规范主机名 |
| MX | 域名 | 邮件服务器名（常再查 A/AAAA） |

### 2.4.5 安全性与工程建议

防范 **DNS 劫持/投毒** 等：DNSSEC、可信解析器、多路径校验、Anycast 与 GSLB 等均为工程常见组合。

## 2.5 P2P 文件分发

> **背诵提纲** → [2.5](./2.5_p2p_file_distribution/study.md)（P2P vs C/S · BitTorrent 七步 · [30 字版](./2.5_p2p_file_distribution/study.md#ch2-5-exam)）

### 2.5.1 数学优势与自我可扩展性

相对纯 C/S，P2P 可利用**群体内聚合上行**，在规模增大时常表现出更好的可扩展潜力（依赖激励与可达性）。

教材常用**最小分发时间**下界（示意，忽略调度细节）：

- **C/S 下界（示意）**：`D_CS ≥ max{ F/u_s, NF/d_min }`  
  - `F`：文件大小；`u_s`：服务器上行；`d_min`：最慢下载链路速率；`N`：对等方数  

- **P2P 下界（示意）**：`D_P2P ≥ max{ F/u_s, F/d_min, NF/(u_s + Σu_i) }`  
  - `Σu_i`：所有对等方聚合上行能力  

当 `Σu_i` 足够大时，第三项可显著缩小，体现 P2P **弹性**。

### 2.5.2 BitTorrent 深度案例

- **最稀缺优先（Rarest First）**：优先请求副本稀少的块，提升块可用性。  
- **Tit-for-Tat**：激励相容；优先回馈高贡献邻居，抑制「搭便车」。

## 2.6 视频流和内容分发网（CDN）

> **背诵提纲** → [2.6](./2.6_video_streaming/study.md)（DASH/MPD · CDN · TCP/UDP · [播放流程](./2.6_video_streaming/study.md#ch2-6-flow) · [30 字](./2.6_video_streaming/study.md#ch2-6-exam)）

### 2.6.1 DASH 协议

**DASH**（基于 HTTP 的自适应流）：客户端按实时带宽在**多码率分片**间切换。核心是 **Manifest（告示/清单文件）**，列出不同质量分片的 URL 与元数据。

### 2.6.2 CDN 架构深度分析

- **Enter Deep**：深入接入网大量部署边缘节点（如 Akamai 类策略）——时延潜力好，运维复杂。  
- **Bring Home**：在 IXP 等关键位置建大规模 PoP（如部分厂商策略）——运维相对集中，边缘密度与 Enter Deep 有取舍。

### 2.6.3 工程实践

**GSLB**（全局负载均衡）结合 **DNS 重定向/调度**，将用户导向延迟与负载较优的边缘节点。

## 2.7 套接字编程：生成网络应用

### 2.7.1 战略背景

**Socket** 是应用进程访问运输层服务的 API。

<a id="ch2-7-udp"></a>

### 2.7.2 UDP 套接字开发

UDP **无连接**：发送方将数据封装进数据报并附上目的 IP 与端口即可发送。

```python
# 简单的 Python UDP 服务器示例
from socket import *

serverPort = 12000
serverSocket = socket(AF_INET, SOCK_DGRAM)
serverSocket.bind(('', serverPort))
while True:
    message, clientAddress = serverSocket.recvfrom(2048)
    serverSocket.sendto(message.upper(), clientAddress)
```

<a id="ch2-7-tcp"></a>

### 2.7.3 TCP 套接字开发

TCP 需先建立连接。服务器通常：**监听套接字** `listen` + **连接套接字** `accept` 分离并发会话。

```python
# 简单的 Python TCP 服务器示例
from socket import *

serverPort = 12000
serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', serverPort))
serverSocket.listen(1)
while True:
    connectionSocket, addr = serverSocket.accept()  # 产生连接套接字
    sentence = connectionSocket.recv(1024).decode()
    connectionSocket.send(sentence.upper().encode())
    connectionSocket.close()
```

### 2.7.4 架构师视野：进阶实践

- **字节序**：跨平台时注意主机序与**网络字节序（大端）**转换（如 `htons` / `htonl` 族）。  
- **并发模型**：一线程一连接易遇内核开销瓶颈；高并发常用 **I/O 多路复用**（如 Linux `epoll`）+ **事件循环**。
