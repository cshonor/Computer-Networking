## 〇、新手易懂版（交通系统类比 · 10 分钟搞懂）

### 一、传统老网络笨在哪？

把**整个网络**类比成**城市交通**：

| 比喻 | 对应 |
|------|------|
| 每个路口的交警 | 传统路由器/交换机 |
| 自己认路、自己定规矩 | **每台设备自己说了算** |
| 全城改限行要跑遍每个路口 | **改规则超级麻烦**，逐台手动配 |

**结果**：网络一大就乱、改配置累死、出问题调不动。

→ 对应考试四痛点：[#ch4-4-pain](#ch4-4-pain)

1. **思考（控制）和干活（转发）绑死**在同一设备  
2. 每个设备**各管各的**  
3. 厂商私有、**改不动**  
4. 新业务上线**极慢**

---

### 二、SDN 是什么？一句话讲透

**SDN = 软件定义网络**

👉 **把「思考决策」和「干活转发」彻底分开！**（**控数分离**）

| 角色 | 交通类比 | 网络对应 | 干什么 |
|------|----------|----------|--------|
| **数据平面** | 路口站岗的**保安** | 交换机/路由器硬件 | **不动脑**，上头让怎么转就怎么转，**速度拉满** |
| **控制平面** | 市中心**交通指挥大厅** | **SDN 控制器**（服务器软件） | **全网上帝视角**，统一算路、定规则，**一键下发** |

✅ 核心：**控转分离** — 大脑在指挥大厅，路口只执行。

<a id="ch4-4-core-verify"></a>

#### 核心分界（终极验证版 · 钉死概念）

**传统**：每一台路由器/交换机 = **自带小控制平面 + 自带数据平面**；每台自己算路、自己决策、自己转发，**各玩各的**。

**SDN 做的事（exactly）**：

1. 把**所有设备身上的「控制平面」拆下来、抽走**
2. **合并集中**成**唯一一个（或一组）全局中央控制器**（统一超级大脑）
3. 剩下所有交换机/路由器**全部降级为纯数据平面**：只**无脑查表、高速转发**，**不再自己算路、做决策**

| 补充 | 说明 |
|------|------|
| 不是简单凑一起 | 集中控制平面有**全网完整地图**（每台设备、每条链路、每处拥堵）→ **全局最优**，不是单台局部小聪明 |
| 分工彻底明确 | 见下表 |

| 角色 | 新分工 |
|------|--------|
| **集中控制器**（唯一大脑） | 算路、定规则、下发指令、**全局管控** |
| **所有交换机**（纯数据面） | 收到指令、**无脑查表**、**高速转发** |

> **SDN = 控制平面集中化，数据平面边缘化、简单化、通用化**

**生活化一句记牢**：**高德总部统一规划路线，司机只按导航开车，不再各自猜路。**

→ 考试精编：[#ch4-4-sdn-core](#ch4-4-sdn-core) · SDN 算路：[5.4 传统 vs SDN 算路](../../05_network_layer_control_plane/5.4_sdn_controller_plane/study.md#ch5-4-routing-compute)

### 三、OpenFlow 是什么？

**OpenFlow = 指挥大厅 ↔ 路口保安 之间的传令语言**

- 控制器用 OpenFlow 给交换机发「行动清单」→ **流表**
- 流表格式：**Match + Action**
  - **Match**：看到什么样的包？（源 IP、协议、端口…）
  - **Action**：做什么？（从 3 号口转发、丢弃、上报控制器…）

**新手秒懂 5 步**（首包流程）：

1. 来一个**陌生包**，交换机不知道往哪送  
2. 交换机**打包上报**中央控制器（Packet-In）  
3. 控制器**全局算好**最优路径  
4. 用 OpenFlow **下发流表**（Flow Mod）  
5. 之后**同款包**直接查表极速转发，**不用再请示**

→ 考试 4 步版：[#ch4-4-flow](#ch4-4-flow)

---

### 四、SDN 好在哪？

1. **改全网不用跑断腿** — 指挥大厅敲代码，**秒级全网生效**  
2. **全局智能调度** — 哪堵了一眼看见，**自动绕路**  
3. **不被硬件厂商绑架** — 普通硬件 + 开放协议也能跑  
4. **极度灵活** — 云数据中心、大内网、运营商、CDN **广泛在用**

→ 详细优势：[#ch4-4-advantages](#ch4-4-advantages)

---

### 五、一眼分清：传统 vs SDN

| 对比项 | 传统网络 | SDN |
|--------|----------|-----|
| 谁决策 | 每台设备**自己** | **中央控制器**统一 |
| 配置 | 逐台敲命令 | **一处编程**，全网生效 |
| 设备角色 | 又思考又干活 | **只干活**，不动脑 |
| 灵活性 | 死板、难改 | **可编程**、极灵活 |

---

### 新手小总结（4 句 + 1 句终极版）

1. 以前：设备**又当大脑又当苦力**，混乱难管  
2. SDN：大脑**抽出来集中管理**，设备只当苦力  
3. **OpenFlow**：大脑和苦力之间的**沟通语言**  
4. **流表**：苦力要遵守的一条条 **Match + Action** 规则  

**终极一句**：**控制平面集中化，数据平面边缘化、简单化、通用化。**

## 一、传统网络核心痛点（必背）

| # | 痛点 | 说明 |
|---|------|------|
| 1 | **控数强耦合** | 路由控制逻辑与数据转发逻辑**集成在同一设备** |

一句话：**每台盒子又算又转，还各配各的，难统一优化。**

## 二、SDN 核心思想（精髓）

**控制平面与数据平面完全解耦（控数分离）**

> 通俗钉死：[#ch4-4-core-verify](#ch4-4-core-verify) — **控制集中、数据边缘化简单化**

| 平面 | 职责 | 能力 |
|------|------|------|
| **数据平面**（转发层） | 交换机 | **高速转发**，**不算路由** |
| **控制平面**（管控层） | **集中式控制器** | 统一拓扑、**算路由**、**下发流表** |

- **全网统一调度**，网络可**软件编程**定义

## 三、SDN 三层标准架构

<a id="ch4-4-three-layer-simple"></a>

### 新手易懂：三层对齐（先理顺再学 OpenFlow）

| 层 | 大白话 | 干什么 |
|----|--------|--------|
| **应用层** | 人/程序**定需求、设规则** | 限流、负载均衡、禁访、优先级… |
| **控制层**（控制平面） | **SDN 控制器**，网络大脑 | 收应用需求 → **算路、生成规则**、全网调度 |
| **转发层**（数据平面） | 所有交换机/路由器 | **只按规则搬包**，不算路 |

```text
应用层（定需求、设规则）
    ↓ 北向接口
控制层（控制器，计算决策）
    ↓ 南向接口（OpenFlow）
转发层（交换机，实际转发）
```

→ 南北向详解：[5.4 分层通俗](../../05_network_layer_control_plane/5.4_sdn_controller_plane/study.md#ch5-4-interfaces-simple)

| 层 | 内容 | 典型组件/业务 |
|----|------|----------------|
| 1 **应用层** | 网络业务 APP | 负载均衡、**流量工程**、防火墙、VPN、监控 |
| 2 **控制层** | SDN **控制器** | OpenDaylight、**Floodlight**、**RYU**、ONOS |
| 3 **数据层** | 可编程交换机 | 支持 **OpenFlow** 的硬件/软件交换机，**纯转发** |

> **北向 API**（应用↔控制器）→ [5.4 南北向通俗](../../05_network_layer_control_plane/5.4_sdn_controller_plane/study.md#ch5-4-interfaces-simple)；控制器故障与多控协同 → [5.4 控制平面](../../05_network_layer_control_plane/5.4_sdn_controller_plane/study.md)

<a id="ch4-4-openflow"></a>

## 四、OpenFlow 协议（南向接口 · 必考）

<a id="ch4-4-openflow-simple"></a>

### 新手易懂：OpenFlow 怎么干活（大白话全流程）

#### 1）OpenFlow 是啥

- **南向接口**最主流协议 → **控制器 ↔ 转发设备** 专用通道  
- 作用：大脑**下发命令**、设备**上报状态**，全靠它传

#### 2）核心武器：流表

每条规则 = **匹配条件 + 执行动作**（考试加 **计数器**）

| 部分 | 识别/做什么 |
|------|-------------|
| **Match** | 包长什么样？源/目的 IP、端口、协议… |
| **Action** | 匹配后干啥？**转发**、**丢弃**、**上报控制器**… |

#### 3）完整工作流程（5 步）

1. **首包到交换机** → 查流表，**没有匹配规则**  
2. 经 **OpenFlow** 把陌生包信息**上报**控制器（Packet-In）  
3. 控制器调**全网拓扑**，用 **Dijkstra** 等**算最优路径**  
4. 经 **OpenFlow** 把流表**下发**给沿途交换机（Flow Mod）  
5. **后续同款包** → 本地查表**快转**，**不再问**控制器  

**额外交互**：链路拥堵/故障 → 交换机**南向上报** → 控制器**重算** → **下发新流表**

→ 算路详解：[5.4 SDN 算路](../../05_network_layer_control_plane/5.4_sdn_controller_plane/study.md#ch5-4-routing-compute)

#### 4）小例子（S1、S2，A → B）

→ 完整双向交流实景：[#ch4-4-openflow-bidirectional](#ch4-4-openflow-bidirectional)（H1→H2 四步 + 故障/查询）

#### 5）三句总结

1. **三层**：应用提要求、控制做决策、转发跑数据  
2. **OpenFlow**：控制器与底层设备的**沟通语言**（南向）  
3. **流表**：陌生流量**请示大脑**，熟悉流量**本地快转**

---

<a id="ch4-4-openflow-bidirectional"></a>

### 实景案例：H1→H2 双向交流（OpenFlow 不是单向下发）

**架构**：应用层 → 北向 → **控制器** → **OpenFlow（南向）** → 交换机

**组网**：H1 — S1 — S2 — H2 · 需求：H1 发数据给 H2

#### 第一步：交换机主动上报（转发层 → 控制层）

1. H1 发包到 H2，包抵达 **S1**
2. S1 查本地流表，**无匹配规则**
3. **S1 经 OpenFlow** 封装未知包信息发给控制器（**Packet-In**）

👉 **转发层主动说话**：「这个包该往哪送？」  
上报含：**源 IP、目的 IP、协议**等 Match 特征

#### 第二步：控制器算路、生成规则（控制层内部）

控制器调**全网拓扑**，最短路径 → **H1 → S1 → S2 → H2**

| 交换机 | Match | Action |
|--------|-------|--------|
| **S1** | 源 H1、目的 H2 | 从**连 S2 的端口**转发 |
| **S2** | 源 H1、目的 H2 | 从**连 H2 的端口**转发 |

#### 第三步：控制器下发规则（控制层 → 转发层）

控制器经 **OpenFlow** 把两条规则分别发给 **S1、S2**（**Flow Mod**）  
交换机**存入流表** → 上级下达指令，**一轮双向沟通完成**

#### 第四步：后续同类包，本地快转

H1 再发包 → S1 **匹配流表**直接转 S2 → S2 转 H2 → **不再上报**

```text
首包：S1 ──Packet-In──► 控制器 ──Flow Mod──► S1、S2
续包：S1 ──Match+Action──► S2 ──► H2
```

---

#### 额外两种双向场景

| 场景 | 谁先说 | 谁回话 |
|------|--------|--------|
| **链路故障** | S1 检测 S1–S2 断链 → **OpenFlow 上报** | 控制器**重算路径** → **下发新流表** |
| **状态查询** | 控制器定时 **OpenFlow 查询**端口/状态 | 交换机**整理数据回传** |

---

#### 交流逻辑（通俗）

| 点 | 说明 |
|----|------|
| **语言载体** | OpenFlow = 双方统一的**话术格式** |
| **交换机发话** | 不懂的包、线路坏了、设备状态 → **主动上报** |
| **控制器回话** | 算好路线、定规矩、查设备 → **下发指令** |
| **规则本质** | Match+Action = 控制器给的**办事标准**；有异常**及时汇报** |

#### 极简小结

**OpenFlow = 双向聊天通道**（不是单纯传规则）

- **转发层**：遇事上报、反馈状态  
- **控制层**：收请示、下发规则、调度管控  

→ 考试消息名：[5.4 Packet-in / Flow-mod](../../05_network_layer_control_plane/5.4_sdn_controller_plane/study.md#ch5-4-controller)

### 研学 / 考试精编

### 1）定位

- SDN **南向接口标准协议**  
- 实现 **控制器 ↔ 交换机** 通信（**不是**北向 REST）

### 2）核心：流表 Flow Table

**流表项 = 匹配字段（Match）+ 流量计数器 + 执行动作（Action）**

| 组成 | 内容（例） |
|------|------------|
| **匹配字段** | 源/目的 IP、源/目的端口、VLAN、协议类型等 |
| **动作指令** | 转发、丢弃、**修改报文**、入队列、重定向 |
| **计数器** | 统计流量大小、**包数量** |

与章级 [Match+Action](../study.md#ch4-4) 一致：不限于「目的 IP → 出端口」，可 ACL、NAT、LB 等（依 pipeline）。

### 3）标准工作流程（4 步）

<a id="ch4-4-flow"></a>

1. 交换机收到**无对应流表项**的**未知报文**  
2. **封装报文上送** SDN 控制器（Packet-In）  
3. 控制器**全局计算**路径，生成流表项**下发**（Flow Mod）  
4. 后续**同类流量**直接**匹配流表高速转发**，**不再上报**

```text
未知包 → 上送控制器 → 算路+下发流表 → 同类包本地 Match+Action 转发
```

> **谁下发** = 控制平面；**谁按表转** = 数据平面（本章）

## 五、SDN 核心优势

<a id="ch4-4-vs-traditional"></a>

## 六、传统路由 vs SDN 路由（本质区别）

| 维度 | 传统路由 | SDN |
|------|----------|-----|
| **架构** | **分布式控制**，每台独立算路由 | **集中式控制**，控制器统一算路 |
| **设备职责** | 设备 **计算 + 转发** | 交换机**只转发**，控制器**只计算** |
| **配置方式** | CLI **逐设备**手工 | 控制器**批量下发**策略 |
| **流量调度** | 就近转发，**难全局最优** | **全网视角**，按需定制路径 |
| **扩展创新** | 依赖设备**固件升级** | 上层 **APP** 快速开发新功能 |

控制平面侧对比表 → [5.4 §五](../../05_network_layer_control_plane/5.4_sdn_controller_plane/study.md)

## 七、考试背诵极简版

### 六句口诀

```text
传统四痛：耦合、逐台、封闭、慢
SDN精髓：控数分离、集中算路
三层：应用—控制—数据（OpenFlow交换）
OpenFlow：南向；流表=Match+计数器+Action
未知流：上送控制器→下发→本地匹配转发
优势：全局视图、可编程、集中运维
```

### 30 字

**SDN 控数分离；OpenFlow 南向流表 Match+Action；未知包上送控制器下发后本地转。**

### 50 字

**传统设备控数耦合、逐台配置；SDN 由集中控制器算路并下发 OpenFlow 流表，交换机只做高速转发。流表项含匹配、计数器与动作；首包无表项则上送控制器，之后同类流量本地匹配转发。**

### 考点速记表

| 点 | 一句 |
|----|------|
| SDN 精髓 | **控数分离** |
| OpenFlow | **控制器↔交换机**（**南向**） |
| 转发依据 | 流表 **Match + Action**（+ 计数器） |
| 经典控制器 | ODL、Floodlight、**RYU**、ONOS |
| 未知流量 | **上送控制器** → 查表/算路 → **下发** → 本地转 |

### 易错点

| 易混 | 纠正 |
|------|------|
| OpenFlow = 北向 API？ | **否**；OpenFlow 是**南向**；北向多为 **REST**（见 5.4） |
| SDN = 没有数据平面？ | **有**；交换机仍在数据平面**按流表转发** |
| 所有包都上送控制器？ | **否**；仅**无流表项/首包**等需决策；命中后**本地转** |
| OpenFlow 只下发？ | **否**；**双向**：Packet-In 上报 + Flow-Mod 下发 + 状态查询 |
| 流表 = 传统路由表？ | **广义 Match+Action**；可匹配五元组等多字段，不限目的 IP |
| 4.4 vs 5.4 | **4.4**：OpenFlow/流表/数据面执行；**5.4**：控制器、南北向、拓扑与下发 |
