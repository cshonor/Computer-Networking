# 4.1 对连接的渴望

> 本章：[chapter-summary.md](./chapter-summary.md#ch04-1) · [4.2 TCP](./02-tcp-connection.md) · [4.3 HTTP 连接](./03-http-connection.md)

## 本节核心目标

说明 **HTTP 事务性能高度依赖底层 TCP**，并记住主要**时延来源**与调优相关机制。

---

<a id="ch04-1-latency"></a>

## 一、HTTP 时延从哪来

除动态页面**服务器处理**外，时延多来自 **TCP 网络路径**：

| 阶段 | 说明 |
|------|------|
| **DNS** | 主机名 → IP |
| **TCP 握手** | SYN / SYN+ACK |
| **请求传输** | 上行报文 |
| **服务器处理** | 生成响应 |
| **响应传输** | 下行报文 |

小对象页面时，**握手 + 慢启动**占比可达 **50%+**。

---

<a id="ch04-1-handshake"></a>

## 二、TCP 握手时延

新连接需 **三次握手**（SYN、SYN+ACK、ACK）。  
事务数据很小时，**建连成本**相对极大 → 催生**持久连接**（[4.5](./05-persistent-connection.md)）。

---

<a id="ch04-1-delayed-ack"></a>

## 三、延迟确认（Delayed ACK）

接收方常把 ACK **缓冲 ~100–200 ms**，试图**捎带**在出站数据里，减少单独 ACK 分组。  
副作用：小 HTTP 请求可能**多等一轮 RTT** 才得到确认。

---

<a id="ch04-1-slowstart"></a>

## 四、TCP 慢启动

新连接初始**拥塞窗口小**，成功发送后再逐步增大。  
**已调谐的旧连接**往往比**刚建的新连接**更快。

---

<a id="ch04-1-nagle"></a>

## 五、Nagle 与 TCP_NODELAY

| 机制 | 行为 |
|------|------|
| **Nagle** | 合并小数据再发，减少小包 |
| **`TCP_NODELAY`** | 禁用 Nagle，小 HTTP 报文**立即发**（常见服务器/客户端设置） |

---

<a id="ch04-1-timewait"></a>

## 六、TIME_WAIT 与端口耗尽

关闭后一端进入 **TIME_WAIT ~2MSL（约 120 s）**，防止旧四元组上的**迟到的段**干扰新连接。

高并发压测时：

- 可用**源端口**有限（如约 6 万）  
- 大量短连接 → **TIME_WAIT 堆积** → **端口耗尽**

> 拓展：`tcp_tw_reuse` 等内核参数在生产环境需权衡 RFC 语义与安全。
